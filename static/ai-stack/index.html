One-glance overview

Slack is the control plane, a task runner runs the agents, and an orchestration layer connects the two. Each agent is a Claude Code session in its own tmux session and git worktree.

Claude Code

Native install. Interactive sessions reach models through a company model gateway; the orchestration layer's headless jobs call claude -p directly.

Settings

  • A larger model by default; subagents also run on a larger model
  • Output style: Learning; fullscreen TUI; auto-compact at 750k tokens
  • Company-managed guard rails apply to every session
  • No custom agents or slash commands; subagent types come from plugins

CLAUDE.md (global, 9 KB)

  • Use yarn; one-line commands copied to the clipboard
  • PR rules: link every artifact, pair cross-repo PRs, attach media from the CLI
  • Review report format and a nit ladder for comments
  • Open a session thread in the personal channel at the start of every task
  • Check non-trivial claims with an independent, adversarial agent

Several repos also have their own repo-level CLAUDE.md.

Hooks

  • Writing-style hook (PreToolUse on the Slack MCP and Bash): injects a writing-voice guide and blocks GitHub comments that lack the agent disclaimer
  • vm-reap (SessionEnd): cleans up test VMs
  • Company-managed guard rails

Task runner

The task runner coordinates agent tasks. Each task is a tmux session running Claude Code, in a git worktree or a plain directory. A daemon tracks status from hook signals. It has a desktop app and a terminal UI; tasks are grouped by project, and the groups are synced from the orchestration layer.

What's configured

  • 9 repos
  • Editor Cursor; harness Claude
  • A manual UI hook "Publish to Pages" sends the publish skill to the session
  • Per-task auto rules: buddy-fixes, ci-fixes, conflict-fixes

How it's used

  • Directory tasks (21 dir/*, 7 btw/*): research, PM and side quests
  • Worktree tasks (8): real branches in product repos
  • *-pm tasks: one long-lived "project manager" agent per project
  • *-will-review tasks: one per PR under review; 12 review sessions on disk
  • cos: the Chief of Staff router (see the orchestration layer)

A PR review queue (prototype) shows a "For you" list of pull requests with Approve, Merge and a button that hands a PR to an agent as a task.

Orchestration layer

About 830 lines of shell and Python, plus prompts. It makes the personal channel a two-way line to every agent and keeps one canvas current.

Safety rails on headless runs

  • Budget cap per run ($0.20 relay, $0.40 on its retry, $1 others) and a 15-minute timeout
  • User hooks disabled; a deny list blocks writes, git, gh comments, merges and web fetches
  • A free preflight check before any model call; hourly backoff after 3 failures
  • Locks stop a job overlapping itself; the PR scanner skips PRs a live session is babysitting

Slack integrations

Channels and surfaces

  • Personal channel: session threads, asks, recaps, the PR scanner thread
  • Status canvas: the live board
  • A second personal channel: weekly wins and PR pulse
  • Internal pages site: every artifact mirrored, grouped by project

Mechanics

  • Slack MCP is the only write path for agents
  • Notification workflow: a Workflow Builder automation that turns tagged messages into a push notification
  • Session thread protocol (a notify skill): open a thread first, poll it every 60 s when the relay is down
  • slack-terminal-bridge: an older MCP relay kept alive by launchd

Lessons

Interactive sessions and headless background jobs can fail independently. Agents can keep working all day while the relay and the canvas go quiet, so a stale board is the symptom to watch for.
